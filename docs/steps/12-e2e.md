## Design

**CLI integration.** The AI/operator workflow stays in the existing CLI so the
fill knowledge is in one place:

```
pdf-go fields  in.pdf -o fields.json                     # probe (already exists)
pdf-go fill    spec.json in.pdf -o filled.pdf            # dry run locally (exists)
pdf-go envelope create --server https://sign.example.org --token $TOK \
                       --template in.pdf --spec spec.json \
                       --parties parties.json --title "Contract" --send
pdf-go envelope get <id> [--watch]        # poll status until settled
pdf-go envelope links <id>                # print links for the operator to send
```

`parties.json` = `[{"email","name","order","reason"}]`. The CLI prints only the
links and ids in JSON, never the party emails in the summary line (privacy).
Server auth uses an API token issued by `signsrv client add`. The CLI never
stores the token; it reads `TOKEN` from the environment.

**e2e test** (`go test -tags e2e ./e2e`), all in one process, `DEV=1`:

1. start server on a random loopback port with a temp DB/keystore/storage
2. `signsrv admin add`, login, create a machine client
3. `pdf-go envelope create ... --send` via the CLI (exec the built binary)
4. read the three links out of `var/outbox/*.eml`
5. for each link, in **random order** (the test shuffles them to prove order is
   free): claim (correct email) -> consent
6. after the last consent, assert the batch ran, the envelope reached `delivered`,
   the final PDF has 4 revisions (template, filled, certified, 3 signatures =
   6 rows total), read the three delivery `.eml`, extract the PDF attachment
7. verify the attachment with `signpdf.Verify` -> 4 signers, `valid:true`,
   signers in `order` with a single batch timestamp, each `Reason` carrying its
   own consent time
8. `signsrv audit-verify`; `GET /envelopes/{id}/report` matches the PDF, and
   `consent_at` values differ from `signed_at` for all three parties
9. assert the log file contains no raw token and no `Bearer` value

Then the negative set, each a subtest: double-consent, expired link,
wrong-claim-email, forwarded link (claim with a different email),
`consent:false`, oversized image, stale `document_sha`, decline, admin-cancel
mid-collection, batch triggered before everyone consented, non-admin on
`/admin/stats`, tampered final file (Gate 2).

**run.sh** runs the suite, prints a table of subtests with exit codes, and keeps
the artefacts in `e2e/out/` for the reviewer to open in a PDF viewer.

## Acceptance

```
./e2e/run.sh                    # 18 phases, ends "acceptance run passed"
go test -tags e2e ./e2e -count=1
pdf-go envelope get <id> --watch   # reaches "delivered" and exits 0
```

Last recorded run: **18 phases, `failures: 0`, 34.4 s**, with real Chrome in
the signing phase. The negatives phase contributes 9 checks and each of them
leaves an evidence file in `reports/`.

The reviewer opens `e2e/out/006-sign-3.pdf` in a desktop viewer and checks the
signature panel shows four entries (one certification + three approvals) with
names, a batch date, a valid timestamp, and that the certification shows
"No changes allowed" / form fields locked.

## Signoff

- [x] Happy path runs green from a clean checkout, no network beyond loopback
- [x] All negative paths assert a state, not only a status code (9 checks: the
      replay of a consent, an expired link, a cancel, 15 consent payload rules,
      a non-PDF upload, the consent limit, the login limit, the link limit,
      caller-minted tokens; each asserts a status **and** a field, and each is
      followed by a check that the record was not damaged)
- [x] Signed artefacts are kept for human inspection
- [x] CLI integration uses the shared fill spec, no duplicated logic
